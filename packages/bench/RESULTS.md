## Runtime

A production build runs the same scenarios for convex/react and for
@reatomized/convex rendered by @reatom/react and by @reatom/jsx. The plain
Reatom columns call the client (`convex.query(ref, args)`, `convex.mutation`);
the `ext` columns build the same models with its extensions
(`withConvexQuery`, `withConvexMutation`, `withConvexPaginatedQuery`). Each
run gets a fresh in-process Convex server (packages/convex-fake-server), client
and container. The column that goes first rotates every iteration, and the workload
order alternates. Times run from the action to the DOM change.

The stress case sends one response for each query-set message. The coalesced
case waits until the queued query-set burst has been processed and sends its
final state in one transition. These are synthetic response shapes, not a claim
about how a deployed Convex backend groups responses.

- mount, update all, update one, unmount: 1000 components, each with its own query. Unmount runs until the server holds no subscriptions.
- shared mount, shared update: 1000 components reading one query.
- optimistic shown, mutation confirmed: a mutation with the same optimistic update on a 100-item list, until the optimistic and then the server result render.
- first page, load more: pages of 25.
- 20 transition burst: 20 transitions in a row, each updating the first of 1000 queries, until the last one renders.
- @reatom/jsx renders lists as reactive array children, which rebuild the list on each change.
